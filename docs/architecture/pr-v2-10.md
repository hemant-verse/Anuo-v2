# PR-V2-10 — Migration Verification and Legacy Boundary Cleanup

## Goal

Verify that active application consumers use the canonical V2 domain/API boundaries, remove dead foundation compatibility code, and establish an automated migration gate before any irreversible legacy data cleanup.

## Completed

- Removed the duplicate `requireOwner()` implementation in `lib/authorization.js`.
- Removed the legacy `lib/api-response.js` response helper; authorization now uses the canonical `lib/response.js` envelope.
- Removed the unused `productCreateSchema` compatibility alias.
- Added `scripts/verify-v2-migration.mjs` and `pnpm verify:v2`.
- Verification scans active source consumers for legacy User/Product/AdminAudit model imports, legacy Product API URLs, and legacy Product/User field names.
- Compatibility adapter route files remain explicitly allow-listed and are not treated as active consumers.
- Verification also asserts the required canonical V2 model/service/route artifacts exist.

## Verification gate

Run:

```bash
pnpm verify:v2
pnpm test
```

The migration gate is intentionally static and safe to run without a database. It does not perform data mutation.

## Legacy deletion policy

The following remain until production/staging caller verification is available:

- `/api/products/create`
- `/api/products/sell`
- `/api/products/feed`
- `/api/products/my-listings`
- `/api/products/product/:id`
- `/api/products/:productId/favorite`
- `/api/user/favorites`
- `/api/products/pending`
- `/api/products/verify`
- `models/product.model.js`

Static verification proves there are no repository callers, but it cannot prove that external clients or deployed older frontends are not still sending traffic. Route deletion therefore remains a deployment/observability decision.

## Data migration policy

No `--cleanup` migration was executed. Legacy fields remain available for rollback until application and data verification are complete.
