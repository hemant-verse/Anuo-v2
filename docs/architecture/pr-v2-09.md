# PR-V2-09 — Admin / Moderation

## Goal

Move administrative product moderation and audit behavior into `server/admin`, expose the canonical admin API, and migrate admin pages away from direct database access and legacy moderation endpoints.

## Canonical API

- `GET /api/admin/products/pending`
- `POST /api/admin/products/:id/approve`
- `POST /api/admin/products/:id/reject`
- `GET /api/admin/audit`

## Ownership

- `server/admin/admin.service.js` owns moderation workflow, pending listing queries, and audit writes/reads.
- `server/admin/policy.js` owns admin-role and moderation-decision rules.
- `models/AuditLog.js` is the only canonical audit persistence model.
- Admin route handlers only authenticate, validate, invoke one service operation, and map the response.
- Admin UI never performs authorization as a security boundary.

## Audit behavior

Every successful APPROVE/REJECT action writes an `AuditLog` record containing the admin, Product resource, action, and previous/new moderation state. No secrets or request bodies are persisted.

## Compatibility

`/api/products/verify` and `/api/products/pending` remain temporary adapters and delegate to the canonical admin service. Their deletion target is removal after migration verification.

## Migration / rollback

No database migration is required for this PR because `AuditLog` is introduced as a new canonical collection and legacy `AdminAudit` is no longer referenced by application code. Existing legacy audit records are not deleted automatically; if historical data must be retained, it should be explicitly migrated in a separate data migration before cleanup.
